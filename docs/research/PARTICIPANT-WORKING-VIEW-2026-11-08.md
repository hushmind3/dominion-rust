# 봇별 작업 문맥 유지와 캐시 실측

## 확인한 결함

운영 방의 같은 봇에서 `cacheKey`, `prefixDigest`, `previousReplyMessageId`가 유지돼도 실제 캐시가 0이었다. 예를 들어 아인즈는 20초 간격의 두 호출에서 신규 입력 1,997, 2,019토큰을 사용했다. 원인은 고정 연결 키만 유지하고 실제 입력은 매번 새로 선택한 데 있었다. 이전 주인 메시지·자기 답변을 선택하는 창이 이동하면서 대화 앞부분이 바뀌었다. 이 구조는 캐시 재사용을 방해한다. 다만 이것이 모든 캐시 실패의 유일한 원인이라고 단정할 수는 없다.

이전의 짧은 봇 두 명 실험은 선택 창이 반복해서 이동하는 조건을 충분히 검증하지 못했다.

## 변경한 동작

- 모든 제공자의 공통 호출 경로에서 세션·참가자별 작업 문맥을 유지한다. 모델 이름에 따른 예외나 수동 설정은 없다.
- 이미 전송한 문맥을 그대로 두고, 출처 ID가 새로운 메시지와 필요한 증거를 뒤에 붙인다. 같은 말이라도 다른 원문 ID면 새 발언이다.
- 실제 저장된 자기 답변을 문맥에 추가한다. 실패·취소된 전송은 작업 문맥을 확정하지 않는다.
- 재시작과 모델·제공자 변경 후에도 공통 참가자 상태를 사용한다. 제공자 캐시의 저장 위치까지 이전된다는 뜻은 아니다.
- 원문·페르소나·공통 지시는 보존한다. 도구 호출·결과는 호출 ID로 연결해 중복 재생을 막는다.
- 페르소나·도구 계약 변경, 대화 초기화, 기억의 폐기·수정·권한·만료 변화에는 문맥을 다시 구성한다. 사용 횟수 같은 통계 변경만으로는 초기화하지 않는다.
- 작업 이력이 한도를 넘으면 기존 문맥 선택기로 새 작업 문맥을 구성한다. 원문 저장소는 지우지 않는다. 현재 요청과 필수 지침을 잘라 숫자만 맞추지 않는다.
- 문맥 관리용 모델 호출, 캐시 적중을 얻기 위한 재호출, 가짜 답변, 캐시 패딩은 추가하지 않았다.

구현: `chat/continuity.rs`의 `project`, `commit_projection`; `context.rs`의 출처 ID; `provider.rs`의 공통 전송 전 투영; `runtime.rs`의 원문 고정과 최종 저장 후 확정. 내부 프레임 정보와 작업 문맥 전체는 제공자 파라미터나 공개 답변 메타데이터로 보내지 않는다.

## 실제 API 결과

원래 방의 9명 페르소나와 공통 지시를 격리 환경에 복사했다. 도구·자동 학습은 끄고 `gpt-6-luna`, 추론 강도 `low`로 확인어를 지정한 뒤 다시 물었다. 운영 방에 시험 발언을 쓰지 않았다.

| 실행 | 전체 입력 | 캐시 입력 | 신규 입력 | 캐시 적중 참가자 | 확인어 회상 |
|---|---:|---:|---:|---:|---:|
| 최종 검증: 첫 호출 | 18,460 | 2,176 | 16,284 | 1/9 | 9/9 |
| 엔진 재시작 후 다음 호출 | 19,514 | 14,720 | 4,794 | 8/9 | 9/9 |

두 번째 호출에서 8명은 각각 신규 입력 267~433토큰이었다. 데미우르고스는 캐시가 0이고 신규 입력 2,204토큰이었다. **전원 해결 또는 캐시 100% 보장을 주장할 수 없다.** 각 발언은 실제 모델 호출 1회였다.

별도의 초기 구현 시험은 9명×3회를 실행했다. 두 번째 회차는 5/9, 엔진을 멈추고 6분 대기한 세 번째 회차는 7/9가 캐시에 적중했다. 확인어 회상은 모두 통과했다. 이 시험은 날짜 중복 제거·증거 무효화 보강 전 구현이므로 최종 코드와 별도 기록했다.

전체 입력은 전송한 문맥 크기이고, 신규 입력은 제공자가 캐시로 처리했다고 보고하지 않은 입력이다. 전체 입력이 줄었다고 표현하면 안 된다. 가격이나 실제 GPU 연산량을 측정한 결과도 아니다. 제공자 캐시 조건·보관 정책은 하네스가 보장할 수 없으며, 상태 없는 API에서는 작업 문맥 자체를 계속 전송해야 한다. [OpenAI 캐시 지침](https://developers.openai.com/api/docs/guides/prompt-caching)

원시 토큰 수와 참가자별 결과는 `benchmark/PARTICIPANT-WORKING-VIEW-2026-11-08.json`에 있다. 이는 짧은 대화의 연속성 검증이며 범용 추론 향상이나 경험 학습 효과의 증거가 아니다.

## 회귀 검증

9명×3회에서 실제 API 요청 앞부분이 이전 요청과 같은지 검사하고, 세 번째 회차 전에 엔진을 재시작한다. 키만 같다는 조건으로 통과시키지 않는다. 모델·프로토콜 변경, 같은 문장의 별도 발언, 도구 짝 중복, 폐기된 지식 무효화, 문맥 한도 초과와 원문 보존도 검증한다.

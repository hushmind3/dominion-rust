# H8 canary 승격 (2026-11-05)

## 1. 실험 승격 후 canary

`improve::apply_experiment_result`가 유리한 격리 실험 결과로 전략을 승격할 때
바로 전체 적용하지 않고 canary로 시작한다.

- `rollout=canary`, `canaryTurns=0`
- `active_values`는 canary 전략을 **결정적 20% 세션**에만 주입한다.
  bucket = `stable_id(sessionId, strategyId)[..8] % 100 < 20` (CANARY_PERCENT)
- 생산 관찰에서 성공 3회(`CANARY_SUCCESSES`)면 `rollout=active`.
- canary 중 `taskOutcome=failed`가 관찰되면 즉시 `rolled_back` + `rollout=halted`.

## 2. 발견·수정한 결함

`execution_updates`가 `status=adopted`만 관찰하고 있었다. 실험으로 `validated`가
된 전략은 이후 관찰을 전혀 받지 않아 canary 승격/롤백이 불가능했다.
→ `adopted | validated`를 모두 관찰하도록 수정. canary가 halted이면 카운터
승격이 이를 덮어쓰지 않도록 가드도 추가했다.

## 3. 검증

- `canary_exposure_is_deterministic_and_partial`
- `a_promoted_strategy_starts_in_canary_and_activates_after_clean_use`
- `canary_failure_rolls_back_before_full_exposure`

전체: `test result: ok. 228 passed` (unit), `30 passed` (E2E), `8 passed` (benchmark).

## 4. 남은 것

- 자동 실험 scheduler(대기 중 전략을 격리 runner에 배정).
- canary 비율/기간 설정 노출, holdout 전이 평가.

## 5. 실험 요청 scheduler

`improve::schedule_experiments`가 `validated + requiresExperiment=true` 전략에
대해 **한 revision당 하나의 durable experiment request**를 만든다.

- 호출 지점: finalize transaction이 `Applied`된 직후, 그리고 엔진 시작 시.
- record: `experiment_request {id, strategyId, revision, status:"queued",
  fixture:"audit_report", minIndependentUnits:8}`
- idempotent: `improvement.experimentRequestId`와 request id로 중복 생성 방지.
- `apply_experiment_result`가 결과를 적용하면 해당 request를 `completed`로
  전환하고 experimentId/verdict/units를 기록한다.
- API: `GET /api/experiment-requests`.

이것으로 **전략 선택/요청 생성은 자동**이다. 실제 격리 실험 실행은 여전히
`target/release/dominion-benchmark`가 담당한다. runner가 production DB의 request를
직접 소비하는 scheduler loop는 다음 단계다.

검증: `observed_strategies_get_one_durable_experiment_request`.

## 6. Runner scheduler loop (2026-11-05)

이제 isolated runner가 production의 queued experiment request를 직접 소비한다.

### 흐름

```
production engine                       benchmark runner
GET/POST 없음                           BENCH_CLAIM_URL=<prod>
   ↑                                         │
   │  POST /api/experiment-requests/claim    │
   │  ← {request, strategy}                  │
   │                                         ├─ 격리 engine 시작 (temp root)
   │                                         ├─ claimed text/verification로 양 arm seed
   │                                         ├─ paired trials
   │  POST /api/experiment-requests/:id/complete
   │  ← {request: completed, promotion: ...}
```

- claim은 CAS(`status=queued → claimed`) + `claimToken` + `claimExpiresAtMs`.
- TTL이 지난 claimed 요청은 다음 claim에서 다시 queued로 회수된다.
- 실패/중단 시 `POST /release`로 반환하며 3회 시도 후 `failed`.
- 완료 시 production 엔진이 `apply_experiment_result`를 호출하므로 승격/롤백/
  canary는 production 정책에 적용된다. runner는 claim 모드에서 로컬 승격을 하지 않는다.
- 결과가 inconclusive여도 request는 `completed`로 종결되고, 승격은 일어나지 않는다.
- runner는 `BENCH_PROVIDER_BASE`로 모델 endpoint를 바꿀 수 있다(테스트/다른 런타임).

### 검증

`the_isolated_runner_claims_and_completes_a_queued_experiment` (E2E):
- production 엔진에 procedure 전략 seed → experiment request queued
- 실제 `dominion-benchmark` 바이너리를 `BENCH_CLAIM_URL`로 실행
- 10 pair, mock provider
- 결과:
  - runner stdout `request completed: completed`
  - production request `status=completed`, `independentUnits=10`
  - 전략 `evidenceGrade=E2`, `validatedBy=isolated_experiment`, `rollout=canary`

`experiment_claim_is_token_scoped_and_can_be_released`:
- 잘못된 token의 complete/release는 409
- release 후 다시 claim 가능, token이 달라짐

전체: `test result: ok. 232 passed` (unit), `35 passed` (E2E), `8 passed` (bench).

### 남은 것

- production 스케줄러가 runner 프로세스를 주기적으로 깨우는 daemon loop(현재는
  runner를 실행하면 1건을 claim).
- claim 만료 회수 후 재시도 정책/알림.
- holdout fixture 전용 request routing.

## 7. Production scheduler daemon (2026-11-05)

production 엔진이 주기적으로 runner를 깨워 queued request를 소비한다.

### 설정

| env | 의미 | 기본 |
|---|---|---|
| `DOMINION_EXPERIMENT_SCHEDULER=1` | daemon 활성화 | off |
| `DOMINION_EXPERIMENT_RUNNER` | `dominion-benchmark` 경로 | 필수 |
| `DOMINION_EXPERIMENT_INTERVAL_SECS` | tick 간격 | 60 |
| `DOMINION_EXPERIMENT_PAIRS` | runner pair 수 | 10 |
| `DOMINION_EXPERIMENT_MODEL` | runner model | qwen3:4b |
| `DOMINION_EXPERIMENT_PROVIDER_BASE` | runner provider endpoint | runner 기본값 |

### 동작

1. tick마다 `experiment_request`에 `status=queued`가 있는지 확인.
2. 있으면 runner 프로세스를 1회 실행:
   - `BENCH_CLAIM_URL=http://127.0.0.1:<engine port>`
   - `BENCH_RUNNER_ID=scheduler-<instance>`
   - `DOMINION_BIN=<current engine binary>`, pairs/model/provider 설정
3. runner가 claim→실험→complete를 수행한다.
4. 프로세스가 실패하면 scheduler가 `release_runner_claims(runnerId)`로
   해당 runner의 claim을 모두 queued로 되돌린다.
5. 결과는 `scheduler_run{status,exitCode,stdoutTail,stderrTail,releasedClaims}`로
   durable하게 남고 `GET /api/scheduler-runs`로 조회한다.

### 검증

`the_production_scheduler_runs_a_queued_experiment_without_manual_invocation`:
- production 엔진을 scheduler env로 기동
- benchmark endpoint로 strategy + experiment request queued 생성
- **수동 runner 호출 없이** 1초 tick으로 runner가 실행됨
- request `status=completed`
- `GET /api/scheduler-runs`에 `status=success`와 runner stdout
  `request completed`가 기록됨
- 통과: `test result: ok. 1 passed` (2.46s, 전체 E2E 38에 포함)

`experiment_claim_is_token_scoped_and_can_be_released`에
`POST /api/experiment-requests/release-runner`로 runner 소유 claim 일괄 반환을 추가 검증.

### 한계

- tick당 runner 1회/요청 1건. 동시에 여러 요청을 병렬 실행하지 않는다.
- 요청별 model/pairs override는 아직 없다(전역 env).
- daemon tick 자체는 in-memory timer이며, 프로세스 재시작 후 다음 tick에서 재개된다
  (요청/claim/실행 기록은 durable).
- runner 실패 시 즉시 requeue하며 지수 backoff는 없다.

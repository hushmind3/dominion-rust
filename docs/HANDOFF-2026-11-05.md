## 다음 담당자가 먼저 해야 할 일

### 1. 일반 채팅 실행의 증거 게이트 완성 — 가장 중요, 아직 미완성

현재 `/goal`에는 실제 증거 검사와 reviewer가 있으나 **일반 채팅 실행은 모델이 실제 도구를 쓰지 않고 ‘저장했다’고 말해도 completed가 될 수 있다.** 이것이 사용자에게 중요한 하네스 결함이다.

- 위치: `src/engine/chat/runtime.rs`
- 준비된 검사 함수: `src/engine/goals.rs`의 `prepare_acceptance_checks(state,input)` / `check_acceptance(state,input,checks,evidence)`
- 보고서 작성 시점 runtime에는 이 검사 호출이 아직 없다. 함수만 추가된 것을 구현 완료로 간주하지 말 것.
- 검사 근거는 실제 주인의 작업 요청이어야 한다. 인용문·예시·다른 에이전트의 말·기술 질문을 실행 지시로 오인하지 말 것.
- 파일 변경 판정의 기준 상태는 **실행 전에** 저장한다.
- 방에서는 `source_message_id`가 가리키는 원문을 사용한다. 합성된 그룹 프롬프트 전체에서 명령을 추론하지 않는다.
- 실제 성공한 도구 결과만 증거로 인정한다. 읽기·실패한 셸·모델의 완료 주장을 파일 쓰기 증거로 인정하지 않는다.
- 증거가 부족하면 기존 실행 예산 안에서 수정 지시를 주고 다시 실행한다. 끝내 근거가 없으면 실패/확인 필요를 반환한다.
- 도구를 꺼둔 요청에 도구를 몰래 켜지 않는다. 실행하지 못한 일을 완료했다고 저장하지 않는다.
- 기존 일반 실행 한도는 8회 모델 라운드·40회 도구·10분이다. 이번 작업에서 줄이지 않았다. 이를 기능 축소 방식으로 해결하지 말 것.

사용자 소유 구판 비교 자료: `/Users/gim-yeonsu/dominion-run/server/harness.mjs`, `execution-runtime.mjs` 및 관련 tests. **구조/동작 비교용이며 코드 복붙용이 아니다.**

### 2. 작업 큐 API와 실행 상태를 네이티브 계약으로 정리

발견한 실제 오류: `ExecutionMonitor`가 `POST /api/jobs`로 작업을 보냈지만 기존 generic JSON 저장은 `status:queued`를 만들지 않아 worker가 실행하지 못할 수 있었다.

- `src/api/jobs.rs`를 새로 만들어 실제 enqueue하도록 수정했다.
- `/api/jobs`를 generic collections에서 제거하고 전용 라우트로 연결했다.
- 작업 생성은 prompt/workflow 입력을 허용하고 클라이언트가 completed/실행 증거를 임의 저장하지 못하도록 했다.
- worker의 prompt 실행이 toolsEnabled/thinking/reasoningEffort를 존중하도록 수정했다.
- **최근 변경이라 최종 통합 검증은 안 했다.** GET job·중단·ExecutionMonitor와의 실제 계약을 확인할 것.
- `/api/executions` 등 나머지 generic runtime 기록 쓰기도 점검이 남았다. 사용자 명령 입력과 엔진이 소유하는 상태/증거 저장을 구분해야 한다.
- 학습 작업이 대화 응답을 지연하지 않도록 큐 우선순위/동시성 조정이 남았다. 기능을 끄는 방식으로 해결하지 않는다.

### 3. 중단·복구·영속성 유지

- 실제 도구 수행 전 operation을 영속화하고 불확실한 외부 변경은 재시작 후 자동 재실행하지 않는 구조가 기존에 있다.
- `run_quiet_outcome`을 추가하여 실행 오류 때도 이미 수집된 성공 도구 증거가 사라지지 않게 했다.
- 도구 성공/실패 카운터의 get→increment→put 경쟁을 `Store::increment_counters`로 바꾸었다.
- `goal_control.rs`는 취소 epoch·job.cancelRequested·저장된 goal 상태를 함께 확인한다. `/goal`의 계획·검토 호출에도 연결했다.
- 일반 채팅·방·작업에도 ‘중단 후 새 대화로 취소 플래그를 해제했을 때 예전 작업이 살아나지 않는지’를 계속 보장해야 한다.

- `main.rs`는 얇은 진입점으로 분리됨: `bootstrap.rs`, `migrations.rs`, `platform/`.
- **중복 실행이 포트 확인 전에 기존 pending 승인을 interrupted로 바꾸던 버그**를 수정했다. 리스너 선점 후에만 DB migration/worker를 시작한다.
- 구형 레코드 migration은 기존 목적지 데이터와 충돌할 때 덮어쓰지 않으며, 저장 성공 전에 원본을 삭제하지 않는다.

- `learning::enqueue_for_agent`가 추가되어 방의 각 참가자에 대해 actor/provider/model/watermark를 고정할 수 있다. **현재 manual learn 핸들러는 기본 enqueue를 쓰므로 방 전체 수동 추출 연결은 미완성이다.** 일반 private chat과 방의 자동 per-agent 추출을 구분해야 한다.
- 학습 enqueue에 원자적 중복 방지를 추가했다. 실패 후 제공자/모델을 바꿔 재시도할 때 동일 snapshot ID 처리 정책은 점검이 남았다.
- 실제 저장 이후 learning_feedback 이벤트·기억 대시보드·근거·교체 이력·스킬 초안을 표시한다. 모델 가중치 재학습 기능은 아니다.
- 외부 참가자의 선호가 주인의 선호를 덮어쓰지 않도록 sourceAuthorKey/provenance를 추가했다.
- 추론을 자동 Google 번역하느라 저장 전에 추가 네트워크 호출을 기다리던 지연 경로를 제거했다. 원문 추론 보존, 첫 토큰/모델/도구 시간 기록. 수동 번역 API는 남아 있다.

### Discord·Telegram

- `bridge.rs`, `telegram.rs`, Discord room 경로 수정으로 웹과 같은 방 원장을 사용한다.
- 실제 외부 토큰은 vault, 사용자 허용 목록, 봇/자기 메시지 루프 차단, 중복 수신 방지, durable outbox, sending 중 재시작 시 자동 중복 송신 금지.
- `syncRoomMessages`는 웹/다른 연결의 새 발언 전달을 명시적으로 켜는 옵션이다. 과거 전체 기록을 갑자기 내보내지 않는다.
- **실제 런타임 채널은 0개다. Discord 서버/채널을 만들거나 실제 Telegram/Discord 메시지를 보내지 않았다.** 기존 외부 봇 및 이 Codex 대화가 자동 연결된 상태가 아니다.
- 사용자 기존 봇들의 아이콘/페르소나 9명은 이전 커밋에서 로컬 DOMINION에 이식되어 있다. 원본 SOUL.md 및 개인 데이터는 runtime에만 있다.

### 선택 기능: /goal

- 기존 작업본에 이미 결정적 증거 검사·독립 reviewer 요청·repair가 있었다. 단순 DONE 문자열로 완료하는 구조는 현재 코드 설명으로 맞지 않는다.
- 부족했던 실제 replan 호출·계획/검토 이력·별도 planner/reviewer 설정·취소 가능한 role 호출을 추가했다.
- 기본 반복16, 기본 재계획6, 수용 조건과 원래 증거를 재계획 때 보존하도록 했다.
- **이 마지막 보강은 최종 통합 검증 전이다. 일반 실행 엔진보다 우선해서 추가 확장하지 말 것.**

### 프론트

- React/Vite/Tailwind4와 공통 Button/TextInput/Panel 등을 유지한다.
- 채팅·방의 상단 중복 제목 축소, 공통 툴바/입력기, 추론 강도·파일·붙여넣기·세션 닫기/보관, 개별 페르소나 체크를 연결했다.
- 도구/MCP/스킬 검색을 하나로 정리했고 가짜 추천/설치 완료 표시는 제거했다.
- **색상 하드코딩과 별도 CSS를 테마 토큰/공통 컴포넌트로 통일하는 작업은 완료하지 않았다.** 새 CSS가 짧은 줄에 압축돼 있으므로 줄 수만 보고 작다고 판단하지 말 것. 사용자는 큰 손 CSS로 돌아가는 것을 원하지 않는다.

### 영상·계정·FreeLLMAPI — 우선순위 낮음

- Rust가 자막 카드 PNG를 만들고 FFmpeg로 무음 MP4를 인코딩하는 실제 큐를 추가했다. AI 촬영 영상 생성이라고 주장하지 않는다.
- 선택형 ComfyUI HTTP workflow, 별도 명시적 YouTube 업로드 job을 추가했다. 실제 YouTube 업로드는 하지 않았다.
- YouTube 업로드는 결정적 job ID로 중복 생성 방지, 결과 저장 후 재시작 시 네트워크 재호출 방지, 불확실한 PUT 결과는 needs_review.
- 미정리: 업로드 아동용 여부가 false로 고정됨, 파일 크기 검사 전에 전체 읽음, native FFmpeg 경로가 frozen job config 대신 현재 설정을 참조함. 배포 전에 수정할 것.
- Google 기본 identity와 YouTube scope/token을 분리하고 PKCE·vault·갱신·시스템 브라우저 동의를 추가했다. OAuth 앱 설정은 사용자/배포자가 필요하다.
- FreeLLMAPI 공식 저장소 `tashfeenahmed/freellmapi`를 확인했다. 선택형 OpenAI 호환 허브 preset/모델·사용량 진단만 추가했다. 외부 엔진을 복사·설치하지 않았다.
- **30개 사이트 가입 자동화·전용 CDP 브라우저·키 수집은 구현하지 않았다.** 사용자가 핵심 엔진에 집중하라고 하여 중단했다. 현재 기능으로 광고하지 말 것.

### Tauri

- Rust host + 자체 Rust backend sidecar + React 정적 자원. Node/Electron 런타임은 쓰지 않는다.
- Mac app/DMG의 첫 빌드는 성공했지만 **그 설치본에는 이후의 모든 최신 변경이 포함돼 있지 않다.**
- 기존4317 엔진을 확인해 재사용하거나 전용 데이터/포트로 자체 엔진을 시작한다. 자기 child만 종료한다.
- parent stdin EOF 때 SSE가 열려 있어도 엔진을 종료하는 경로가 있다.
- 같은 코드베이스 Windows NSIS/MSI + Mac ARM/Intel CI workflow 작성. **Windows 빌드/CI 실행·새 릴리스 게시·최신 설치본 배포는 하지 않았다.**
- 기존 `/Applications/DOMINION.app`을 이번 최신 Tauri 앱으로 교체하지 않았다.

## 검증 기록과 정확한 한계

- 마지막 성공한 전체 실행: `cargo test --release` → **110 unit + 8 integration 통과**.
- 이는 API 도메인 분리, 최신 goal 보강, native jobs API, 최종 일반 실행 게이트 작업 **이전**의 결과다. 현재 전체 작업 트리의 통과라고 보고하면 안 된다.
- 이후 Chat 모듈 분리/일부 bootstrap 검사는 별도로 통과했고, 최근 `cargo check`는 성공했다. 최종 변경 이후 전체 테스트는 안 돌렸다.
- UI 최근 TypeScript 검사는 통과했다. 일부 변경 전 production build도 성공했다.
- 격리 UI에서 글자/공간·이미지 붙여넣기·실제 무음5초MP4 생성은 확인했지만, 실계정 OAuth/외부 API/Discord/Telegram/YouTube 실사용 검증은 하지 않았다.
- 사용자가 추가 검증을 직접 하겠다고 하여 더 이상 검증을 확대하지 않았다.

## 실행 환경 주의

- 기존 서비스: `127.0.0.1:4317`, launchd `com.hushmind.dominion.rust`.
- 격리 화면 확인용 서버: `127.0.0.1:4327`, 데이터 `/private/tmp/dominion-ui-check`. 이 서버에 9명 test-agent와 테스트 작업이 있다. 실계정/채널/키 없음.
- `web/dist`가 새로 만들어져 **기존4317 백엔드 바이너리와 최신 UI API가 일시적으로 맞지 않을 수 있다.** 최신 소스 빌드·서비스 재시작은 아직 하지 않았다.
- runtime 백업·DB·키·개인 페르소나·모델·target·node_modules·dist는 커밋하지 않는다.
- 작업 트리에 변경과 신규 파일이 매우 많다. `git diff --stat`는 untracked 신규 모듈을 포함하지 않으므로 삭제량만 보고 기능이 지워졌다고 판단하지 않는다.

## 인계 후 최소 진행 순서

1. 현재 변경을 보존하고 일반 채팅의 실제 실행/증거/수정 루프부터 완성한다.
2. native jobs API와 취소·복구·학습의 API 계약을 맞춘다. DB에 임의 JSON을 저장하고 실행됐다고 간주하지 않는다.
3. 파일 이동/미완성 연결을 정리하고 필요한 컴파일 확인을 한다. 사용자 검증 범위는 사용자와 맞춘다.
4. 최종 소스 기준 실행 바이너리·UI·설치본을 함께 갱신한다.
5. 사용자가 원했던 push를 할 때 작업 브랜치뿐 아니라 **main 반영 여부를 명확히 한다.** 이번 작업은 아직 푸시되지 않았다.

# H4 RunCoordinator 1단계 — durable run lease (2026-11-05)

H4 전체(RunCoordinator 상태 reducer, lease/wake, 단일 lifecycle) 중 **소유권·생존
신호·재시작 복구**를 실제 실행 경로에 먼저 연결했다.

## 1. 계약

- lease key: `session:{sessionId}`. chat, goal, room, workflow turn은 모두
  `run_turn_with_policy`를 지나므로 같은 lifecycle을 공유한다.
- owner: `instanceId:uuid`. 프로세스가 아니라 **turn 하나**가 소유자다. 같은
  엔진에서 두 turn이 동시에 같은 세션을 소유할 수 없다.
- `expiresAtMs`: TTL 120초. heartbeat가 TTL/3(최소 1초)마다 갱신한다.
- heartbeat는 turn이 승인 대기나 긴 모델 호출로 멈춰 있어도 계속 돈다.
- turn 종료 시 guard Drop이 heartbeat를 중단하고 lease를 삭제한다.
- 엔진 시작 시 `migrations::stale_leases`가 다른 owner 또는 만료 lease를 제거한다.
  이 프로세스는 포트 바인딩과 duplicate-start guard를 통과한 유일한 소유자다.
- 실행 기록은 기존 `interrupted_executions` 마이그레이션이 `interrupted`로
  종결하므로, 재시작 후 lease 회수와 실행 상태 종결이 함께 일어난다.

## 2. 구현

| 파일 | 변경 |
|---|---|
| `src/db.rs` | `acquire_lease`, `renew_lease`, `release_lease`, `release_stale_leases`, `active_lease` |
| `src/engine/lease.rs` | `LeaseGuard` + heartbeat task + Drop release |
| `src/state.rs` | 프로세스 `instance_id` |
| `src/migrations.rs` | 시작 시 stale lease 회수 + audit |
| `src/engine/chat/runtime.rs` | 세션 진입 시 lease 획득, 실패 시 실행 거부 |

## 3. 검증

- `cargo test --release`: **217 unit + 29 E2E + 8 benchmark bin**
- `run_leases_are_exclusive_and_recover_after_crash`
  - 살아있는 lease는 두 번째 owner 거부
  - 다른 owner renew 거부
  - 만료/외부 owner는 시작 시 회수
- `a_session_has_one_live_owner_and_is_released_on_drop`
- `heartbeat_keeps_a_long_turn_alive` (TTL 1.5초, 1.7초 대기 후에도 lease 유효)
- E2E `approval_is_operation_bound_and_survives_restart`
  - 실행 중 프로세스 kill → 같은 data root 재시작 → 승인 → 같은 task 재개 성공.
    이 경로는 시작 시 lease 회수가 없으면 실패한다.

## 4. 아직 아닌 것

- RunCoordinator의 계획 상태 reducer(reactive/outline/graph 선택·재계획) 통합.
- lease 만료 시 **자동 wake/retry** 정책(현재는 회수 후 다음 요청이 재개).
- 다중 프로세스에서의 lease 조정과 fencing token. 현재는 단일 엔진 전제다.
- 장기 soak에서 heartbeat/DB 경합 측정.

## 5. 두 번째 정책 슬롯: recovery (2026-11-05)

계획(planning)만 소비되던 정책 슬롯에 `recovery`를 추가하고 실제 런타임 분기에 연결했다.

### 파라미터

`policy::recovery_limits(parameters) -> (acceptance_retries, procedure_repairs)`

- `maxAcceptanceRetries`: 기본 2, 0..4로 clamp
- `maxProcedureRepairs`: 기본 2, 0..4로 clamp
- 정책은 안전 한도를 조정할 수 있지만 제거할 수는 없다(최대 4).

### 런타임 연결

- `run_turn_body`가 active `recovery` 정책을 읽어
  `acceptance_retries < max` / `procedure_repairs < max` 분기에 사용한다.
- 적용된 recovery 정책은 selection snapshot의 `contextItems`에
  `kind=recovery_policy, id, revision, parameters`로 고정된다.
- 활성 정책이 없으면 기존 값 2/2로 동작해 회귀가 없다.

### 실험 gate

모든 슬롯이 동일한 gate를 쓴다.

- `independentUnits >= 8`
- 유리한 verdict + success delta > 0
- main semanticDelta >= 0.05 **그리고** independent semanticDelta >= 0.05

recovery 슬롯도 이 조건을 통과해야 active가 된다.

### 검증

- `recovery_limits_are_bounded_and_configurable`
  (기본 2/2, 0 허용, 99 → 4 clamp)
- `a_recovery_policy_uses_the_same_experiment_gate`
  (4 units → candidate, 8 units + 두 evaluator → active)
- E2E `the_recovery_slot_changes_retry_behavior_only_after_a_valid_experiment`
  - 후보 상태 + 4-unit 실험: 채팅 스트림에 `acceptance_retry` 존재 (행동 변화 없음)
  - 8-unit + 두 evaluator 실험 → active
  - 같은 채팅에서 `acceptance_retry` 없음, execution failed
  - 정책 `slot=recovery`, `status=active`

전체: `254 unit + 43 E2E + 14 benchmark` 통과.

### 한계

- 슬롯은 아직 planning/recovery 두 개다.
- recovery 슬롯의 실험은 planning semantic metric을 proxy로 사용한다.
  재시도/복구 품질 전용 evaluator는 아직 없다.
- retry 상한은 4로 제한되어 있다.

## 1. 이번에 닫은 결함

### D05 — DAG node/edge 증명

- `procedure::evaluate`가 `nodes`/`edges`를 실제 operations와 대조한다.
- node는 `operation_succeeded`(status=completed + error 없음 + success!=false +
  exitCode=0 + HTTP status<400)일 때만 완료 영수증으로 인정한다.
- edge는 `from` 완료 시각(operation 순서)이 `to`보다 앞설 때만 통과한다.
- 실패/거부/중단된 선행 노드는 완료로 취급되지 않는다.

### D06 — 같은 node id 격리

- operation 레코드에 `procedureStrategyId`, `procedureRevision`을 저장한다.
- `ready_intent`, `evaluate`, harness 결과 map 모두 `(strategyId, revision, nodeId)`로
  필터링한다. 서로 다른 전략의 동일 node id가 섞이지 않는다.

### D03 — selection snapshot

- snapshot hash가 contract/strategies/decisions/contextItems/memoryWatermark/
  verificationOwner 전체를 포함한다.
- 검증 실패나 저장 실패를 `let _`로 무시하지 않는다. 스냅샷 없이 실행하지 않고
  해당 attempt를 `failed`로 종결한 뒤 오류를 반환한다.

### D02 — 선택 확률 정직성

- legacy selector는 첫 후보를 결정적으로 고른다. 후보 확률을 균등 1/N로
  기록하던 것을 one-hot(선택 1.0, 나머지 0.0)으로 바꿨다.
- `decision.probability = 1.0`과 후보 분포가 이제 일치한다. IPS/DR 자료로
  오용될 여지를 줄였다.

### D12 — 승인 내구성

- 승인 record가 `runId`, `operationId`, `argsDigest`(canonical JSON)를 가진다.
- 승인 record 저장 실패 시 도구를 실행하지 않는다(fail-closed).
- 승인 해결은 `Store::patch_if` 기반 CAS다. 두 번 resolve해도 첫 결정이 유지된다.
- 엔진 재시작 시 pending 승인은 `interrupted` + `orphaned=true`로 보존된다.
- 재시작 후 승인하면 `resolved=true, resumed=false`로 기록되고, 같은 세션에서
  **동일 도구·동일 인자 digest**의 재시도가 그 승인을 **한 번만** 소비한다.
- 거부(denied)는 재사용하지 않는다. 재시도는 다시 물어본다.
- E2E: `approval_is_operation_bound_and_survives_restart`
  (실행 중 승인 요청 → 프로세스 kill → 같은 data root 재시작 → 승인 →
  동일 세션/인자 재시도 → 파일 생성, pending 승인 없음).

### D15 — finalize hash

- payload hash가 mutable counters/timings/`finishedAt`을 포함하던 것을
  불변 의미 필드만으로 계산하도록 바꿨다.
- 재시도해도 같은 attempt면 같은 hash가 나오고, `taskOutcome` 등 의미가 바뀌면
  다른 hash가 나온다. (단위 테스트 포함)
- `adaptation_finalizations.evaluation_revision`에 payload hash를 중복 저장하던
  것을 `evaluator:finalize-semantic-v1` 상수로 분리했다.

### D14 — 동시 finalize 카운터 유실

- `improve::execution_updates`가 절대값만 돌려주고 `finalize_once`가 레코드 전체를
  upsert하던 경로를 바꿨다.
- 업데이트에 `__counterDelta`(uses/successes/failures 증분)를 실어 보내고,
  `finalize_once` transaction 안에서 현재 레코드에 증분을 더한다.
- `appliedExecutionIds`는 transaction 안에서 dedupe·cap 200으로 병합한다.
- 상태 승격은 악화 방향으로 덮어쓰지 않는다(`rolled_back` > `validated` > 기존).
- 단위 테스트 `concurrent_finalizations_merge_improvement_counters`:
  같은 improvement에 두 attempt가 각각 +1 → uses 5→7, 적용 ID 2개.
- 남은 한계: 승격 판단 자체는 merge 이전에 계산된 누적값을 사용한다. 승격
  시점이 한 표본 앞설 수 있으나 카운터 유실은 발생하지 않는다.

### D16 — compliance 집계

- 하나라도 `followed`면 전체를 Followed로 만들던 집계를 고쳤다.
- 우선순위: `unknown/invalid` → `violated` → `followed` → `not_triggered` →
  `not_applicable`. 위반이 다른 전략의 준수로 가려지지 않는다.
- 단위 테스트 `compliance_summary_prefers_violation_over_followed`.

### 도구 실행 권한 분리

- `toolsEnabled` = 모델의 직접 도구 호출 허용.
- `toolsExecutionEnabled` = 전체 도구 실행 권한(모델+harness 공통).
- harness는 `toolsExecutionEnabled=true`면 `toolsEnabled=false`여도 실행된다.
- 전체 실행이 금지되면 모델/절차 어느 쪽도 도구를 실행하지 않는다.
- E2E `harness_assisted_executes_dag_nodes_through_the_common_dispatch`에
  `toolsExecutionEnabled=false` 차단 케이스를 포함했다.

## 3. 실행 경로

- 모델 도구 호출: `run_turn_body` → `dispatch_tool_call` → approval → operation 기록
- harness 절차: `run_harness_nodes` → `dispatch_tool_call`(동일 경로) → approval/budget
- 승인: `request_approval` → durable record → SSE/이벤트 → `resolve_approval` CAS
- 종결: `finalize_execution` → immutable semantic hash → `finalize_once` transaction
